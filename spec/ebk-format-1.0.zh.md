# EBK 格式规范，1.0 版

状态：候选发布稿，2026-10-02。本文是规范的中文文本（规范是用中文起草的）；`ebk-format-1.0.md` 是英文文本，两者不一致时以英文为准。
参考实现：`crates/ebk`（读取器和写入器）、`crates/ebk-cli`（转换器）。
0.x 是草案，彼此之间以及与 1.0 之间都不兼容。许可：CC BY 4.0。

文中"必须""不得""应当""可以"分别对应 RFC 2119 的 MUST、MUST NOT、SHOULD、MAY。标明"非规范性"的段落、括号里的理由和实测数字不是要求。

## 1. 概述

EBK 是一个只读的电子书容器，由 EPUB 转换生成。它保存 EPUB 里的每个文件（下称**成员**）的路径和原始字节，
阅读器按路径取出成员后，交给现有的 EPUB 渲染器处理。EBK 不定义新的内容模型，也不保证能还原出原来的 EPUB 文件（ZIP 的结构、顺序、时间戳都不保留）。

设计目标：

- 文本类成员合并后分块压缩，体积接近整本固体压缩，同时打开任一章只需解压少数几个块。
- 读取任一成员得到的字节与 EPUB 里的原始字节完全相同（每个成员有校验值）。
- 读取器面对损坏或恶意构造的文件，要么返回正确的字节，要么报错，不得崩溃、越界或无限制地占用内存。

格式**不提供防篡改**：校验值只用来发现意外损坏和实现错误，任何人都可以改动内容后重新算出校验值。

文件扩展名 `.ebk`；媒体类型暂用 `application/x-ebk`。

## 2. 基本约定

- 多字节整数一律小端序。`u8`、`u16`、`u32` 是定长无符号整数。
- **varint** 是无符号 LEB128：每字节低 7 位是数据，最高位为 1 表示后面还有字节，低位组在前。数值不超过 2^63−1，所以最多 9 个字节。
  必须是最短形式：多于 1 个字节的 varint 的最后一个字节不得是 0x00。读取器必须拒绝第 9 个字节最高位仍为 1 的、以及不是最短形式的 varint。
- **CRC-32** 指 ZIP、PNG 使用的那一种（多项式 0xEDB88320，初值和终值异或 0xFFFFFFFF）。
  选它的原因是 EPUB 的 ZIP 目录里已经有每个成员的同一种校验值，转换器可以直接对照。
- **合法的 UTF-8** 指 RFC 3629 的定义（不含代理码位，不含过长编码，不超过 U+10FFFF）。
- 所有长度和偏移的运算（加法，以及 `4 × 存储长度` 之类的乘法）都必须按 64 位无符号数做并检查溢出，在通过范围检查之前不得截断成更窄的类型。
- **精确的 brotli 流**：本规范说"一段长 c 字节的数据是原始长度 n 的精确 brotli 流"，指它同时满足：
  1. 是一个 RFC 7932 的流，流头声明的窗口不超过 2^24（不得使用大窗口扩展），不使用共享字典；
  2. 流恰好在第 c 个字节结束（之后没有多余的输入）；
  3. 解压输出恰好 n 个字节。

  读取器必须检查全部三条，解压时不得产生超过 n 个字节的输出。
- **长度上限**：文本块和索引的压缩长度 c 还必须满足 `1 ≤ c ≤ n + n div 4096 + 64`。这个上限用来防止在流里夹带大量不产生输出的数据。
  brotli 的格式总能做到这一点（压不动的数据可以原样存放），但编码器不保证：实测 Rust 的 `brotli` 在质量 0 和 1 下对随机数据的输出会超出。
  写入器必须检查自己的输出，超出时换一种设置重新压缩（本实现改用质量 2）。

## 3. 文件结构

```
+----------------+  偏移 0
| 文件头  16 字节 |
+----------------+  偏移 16
| 文本块区        |  文本块 0..B-1 依次紧挨着存放
+----------------+
| 资源区          |  资源项依次紧挨着存放
+----------------+
| 索引            |  一个 brotli 流
+----------------+
| 文件尾  16 字节 |
+----------------+  文件末尾
```

各区之间没有填充，也没有显式的偏移字段：文本块区从偏移 16 开始，长度是所有块的压缩长度之和；资源区紧随其后，长度是所有资源项的存储长度之和；
索引的位置由文件尾给出。读取器必须检查

```
16 + 文本块区长度 + 资源区长度 + 索引压缩长度 + 16 == 文件长度
```

不相等就拒绝整个文件。这样文件的每个字节都恰好属于一个被索引描述的区域。
（这不等于每个字节的内容都被检查过：读取器不认识的存储方式的成员、可选的索引段，内容是不透明的。）

### 3.1 文件头（16 字节）

| 偏移 | 类型 | 内容 |
|---|---|---|
| 0 | 8 字节 | 魔数 `89 45 42 4B 0D 0A 1A 0A`（`\x89EBK\r\n\x1A\n`，与 PNG 同样的构造，用来发现文本模式传输造成的损坏） |
| 8 | u8 | 主版本号：1 |
| 9 | u8 | 次版本号：0 |
| 10 | u16 | 标志位。目前全部保留，必须为 0 |
| 12 | u32 | 保留，必须为 0 |

读取器必须拒绝：魔数不符、主版本号不认识、标志位或保留字段不为 0 的文件。

1.0 的读取器必须接受主版本号为 1 的任何次版本。以后的次版本只增加读取器可以安全忽略或局部拒绝的内容
（新的可选索引段、新的成员存储方式、新的码表布局）；可选段不得改变必需段和成员字节的含义。
（0.x 是草案，彼此之间以及与 1.0 之间都不兼容。）

### 3.2 文件尾（16 字节）

| 偏移（相对文件尾起点） | 类型 | 内容 |
|---|---|---|
| 0 | u32 | 索引的压缩长度（字节） |
| 4 | u32 | 索引解压后的长度（字节） |
| 8 | u32 | 索引解压后内容的 CRC-32 |
| 12 | 4 字节 | 结束魔数 `45 42 4B 1A`（`EBK\x1A`），用来发现文件被截断 |

索引的起始偏移 = 文件长度 − 16 − 索引的压缩长度。

### 3.3 打开文件的步骤

读取器必须按下面的顺序检查，任何一步不通过都拒绝整个文件：

1. 文件长度不小于 32；读文件头并检查（3.1）。
2. 读文件尾，检查结束魔数；索引的两个长度各不超过 64 MiB，压缩长度不超过文件长度 − 32，并满足第 2 节的长度上限。
3. 读出索引，按"精确的 brotli 流"解压，核对 CRC-32。
4. 解析各段（第 5 节）及其各自的检查。
5. 交叉检查：文本块的原始长度之和等于文本流长度（第 4 节）；本节开头的文件长度等式成立；码表段存在当且仅当有成员使用码表。

通过网络按范围读取时，文件头和文件尾可以并行获取（例如同时请求前 16 字节和末尾 64 KiB），之后按需取块或资源项。

## 4. 文本流与文本块

存储方式为"块内"的成员（见 5.4）按它们在成员表里出现的顺序，把各自的**存储字节**首尾相接，构成一条逻辑上的**文本流**，总长 L。
成员在文本流里的偏移不单独记录，等于排在它前面的所有块内成员的存储长度之和。长度为 0 的块内成员不占字节（它的偏移可以等于 L）。

文本流被切成 B 个**文本块**，第 i 块覆盖文本流里紧接着前一块的 `r_i` 个字节；`r_i` 记录在块表里（5.2）。

- 每块的原始长度满足 `1 ≤ r_i ≤ 2^24`（16 MiB），且所有 `r_i` 之和必须等于 L。L 为 0 时 B 必须为 0。
- 除最后一块外，每块的原始长度不得小于 4096。理由：每个块都有固定的开销（块表条目、一次解压的启动），
  没有下限的话一个文件可以用十万个 1 字节的块让读取器做与内容不成比例的工作。有了下限，块数不超过 L div 4096 + 1。
- 每块的数据是原始长度 `r_i` 的精确 brotli 流，并满足第 2 节的长度上限。
- 块的边界可以落在成员中间，也可以与成员边界对齐，由写入器决定。
- 读取一个存储长度不为 0 的块内成员（文本流偏移 o、存储长度 n），需要解压覆盖 `[o, o+n)` 的那些块。

块长度可变是为了让写入器把块切在成员边界上（一章不跨块），并把打开书时最先需要的少量成员单独放进一个小块（不小于 4096 字节）。写入器的建议做法见第 9 节。

## 5. 索引

索引解压后是若干个**段**的序列：

```
段 := 标签 u8, 长度 varint, 内容（长度个字节）
```

- 段按标签值从小到大排列，每种标签最多出现一次。
- 标签小于 0x80 的是**必需段**：读取器遇到不认识的必需段必须拒绝文件。标签不小于 0x80 的是**可选段**：读取器不认识就跳过。
- 段的内容必须恰好用完它声明的长度；所有段必须恰好用完索引。

### 5.1 段一览

| 标签 | 名称 | 是否必须出现 |
|---|---|---|
| 0x01 | 块表 | 是 |
| 0x02 | 码表 | 只要有成员使用码表（存储方式 1）就必须出现，否则不得出现 |
| 0x03 | 成员表 | 是 |

### 5.2 块表（0x01）

```
块数 B          varint          不超过 2^20，且不超过段里剩余字节数的一半
B 个条目：
  原始长度 r_i   varint          1 到 2^24；除最后一个条目外不小于 4096
  压缩长度 c_i   varint          1 到 r_i + r_i div 4096 + 64
```

第 i 块在文件里的偏移 = 16 + 前 i 块的压缩长度之和；它在文本流里的偏移 = 前 i 块的原始长度之和。

### 5.3 码表（0x02）

```
布局     u8        本版本只定义布局 1
字符表   若干字节   占满段的剩余部分
```

布局 1 的字符表是一段合法的 UTF-8，列出本书使用码表的成员里出现的非 ASCII 字符。字符在表里的序号（从 0 开始）称为它的**排名**，排名决定编码（第 6 节）。
读取器必须检查：是合法的 UTF-8；每个字符的码位大于 U+007F；没有重复；字符数不超过 8128。任何一条不满足都拒绝文件。字符数可以为 0。

写入器应当按使用频率从高到低排列，频率相同的按码位从小到大，这样不同的写入器对同一本书给出相同的字符表。读取器不依赖这个次序的来历。

读取器遇到不认识的布局时不得拒绝整个文件，但读取任何存储方式为 1 的成员都必须报"不支持"；此时字符表的内容不做检查。
5.1 节的规则与布局无关：没有成员使用存储方式 1 而码表段存在的文件，无论布局是否认识，都必须拒绝。

读取器必须先检查字符表的字节数（不超过 4 × 8128），再解码；字符表所在的段可以和索引一样长。

### 5.4 成员表（0x03）

```
成员数 M        varint          不超过 2^20，且不超过段里剩余字节数除以 9
M 个成员条目
```

M 可以为 0。每个成员条目：

```
存储方式        u8
路径长度        varint        （字节数，1 到 1024）
路径            路径长度个字节
原始长度        varint        成员原始字节的长度
存储长度        varint        成员在文本流或资源区里占的字节数
CRC-32         u32           成员原始字节的 CRC-32
```

所有条目的布局相同，所以读取器不认识某个成员的存储方式时仍然能解析整张表。

| 存储方式 | 位置 | 存储字节的含义 | 读取器必须检查的约束 |
|---|---|---|---|
| 0 | 文本流 | 原始字节 | 存储长度 = 原始长度 |
| 1 | 文本流 | 原始字节经码表编码（第 6 节） | 原始长度 ≤ 4 × 存储长度，存储长度 ≤ 2 × 原始长度 |
| 2 | 资源区 | 原始字节 | 存储长度 = 原始长度 |
| 3 | 资源区 | 原始长度的精确 brotli 流 | 1 ≤ 存储长度 < 原始长度 |
| 4 | 资源区 | JPEG 的可逆再压缩，Lepton（第 7 节） | 1 ≤ 存储长度 < 原始长度 ≤ 2^27，且原始长度 ≤ 8 × 存储长度 |

- 存储方式为 0、1 的成员是**块内成员**，其余是**资源项**。两类成员在表里可以交错出现。
- 存储方式 1 的两条长度约束对任何布局都检查，包括读取器不认识的布局：以后定义的布局也必须满足它们。
- 资源项在文件里的偏移 = 16 + 文本块区长度 + 表里排在它前面的所有资源项的存储长度之和。
- 长度为 0 的成员只能用存储方式 0 或 2，CRC-32 为 0。
- 存储方式不小于 5 的值留给以后的版本。读取器遇到不认识的存储方式不得拒绝整个文件，但读取该成员时必须报"不支持"。
  这样的成员一律按资源项计算偏移（即以后新增的存储方式只能是资源项）。
  读取器不检查这类成员的原始长度与存储长度之间的关系（那由定义它的版本规定，上一条"长度为 0"的规则也不适用），
  但存储长度照常计入偏移，文件长度等式（第 3 节）照常必须成立。读取这类成员时先报"不支持"，不因为它声明的长度报"过大"。

**路径**与该成员在 EPUB 容器里的路径相同（如 `OEBPS/chapter1.xhtml`）。读取器必须检查每个路径：

- 是合法的 UTF-8，不含 U+0000–U+001F、U+007F 和反斜杠；
- 不以 `/` 开头或结尾，不含空的路径段（连续的 `/`）；
- 没有等于 `.` 或 `..` 的路径段；
- 在成员表里不重复；
- 不是另一个成员路径的目录前缀（不能同时有 `a` 和 `a/b`）。

任何一条不满足都拒绝文件。路径的比较和查找一律按字节精确比较，不做大小写折叠，也不做 Unicode 规范化
（格式不要求大小写或规范化意义上的唯一，因为那需要 Unicode 数据表，不同版本的读取器会对同一个文件是否合法得出不同结论）。

## 6. 码表编码（布局 1）

码表编码把一段合法的 UTF-8 文本逐字符改写成另一种字节序列，让常用的非 ASCII 字符只占 1–2 个字节。它只作用于存储方式为 1 的成员；
一本书只有一张码表。原始字节不是合法 UTF-8 的成员不得使用码表（写入器应当用存储方式 0 保存它）。

对文本里的每个字符（Unicode 标量值）c：

| 条件 | 输出 |
|---|---|
| c ≤ U+007F | 1 个字节：c 本身（0x00–0x7F） |
| c 在字符表里，排名 r < 64 | 1 个字节：`0x80 + r`（0x80–0xBF） |
| c 在字符表里，排名 64 ≤ r < 8128 | 2 个字节：`0xC0 + (r−64) div 128`（0xC0–0xFE），`0x80 + (r−64) mod 128`（0x80–0xFF） |
| c 不在字符表里（且 c > U+007F） | 4 个字节：`0xFF`，`0x80 + (c >> 14)`，`0x80 + ((c >> 7) & 0x7F)`，`0x80 + (c & 0x7F)` |

写入器必须对每个字符使用表中第一条适用的规则（即字符表里有的字符不得用 4 字节形式）。

解码从成员存储字节的开头开始，按首字节决定形式：

```
b < 0x80            → 字符 b
0x80 ≤ b ≤ 0xBF     → 排名 b − 0x80 的字符
0xC0 ≤ b ≤ 0xFE     → 再读 1 个字节 t（必须 ≥ 0x80），排名 64 + (b − 0xC0)·128 + (t − 0x80) 的字符
b = 0xFF            → 再读 3 个字节 x y z（都必须 ≥ 0x80），码位 ((x−0x80) << 14) | ((y−0x80) << 7) | (z−0x80)
```

读取器遇到以下任一情况必须报错，不得输出该成员：

- 存储字节在一个多字节形式的中间结束；次字节小于 0x80；
- 排名不小于字符表的字符数；
- 4 字节形式给出的码位不大于 U+007F、大于 U+10FFFF、落在 U+D800–U+DFFF，或者这个字符其实在字符表里；
- 解码结果的 UTF-8 长度不等于成员的原始长度，或 CRC-32 不符。

说明（非规范性）：

- 布局 1 的字节范围是有意这样划分的：单字节码落在 UTF-8 的"后续字节"范围，双字节码的首字节落在 UTF-8 的"首字节"范围，与 brotli 内置的字节分类一致。
  实测（N=64）：中文省 9.5–9.8%（GB18030 只省 4%），日、韩文 7.3–7.9%，其它非拉丁文字 4.6–10.3%，越南文 3.2%，拉丁字母的欧洲语言 0.3–1.7%。
- 这种编码不能自同步：次字节的范围与其它形式重叠，所以只能从成员的开头解码。
- 写入器应当逐本比较：使用码表后整本更小才使用，否则所有成员都用存储方式 0 且不写码表段。字符表本身对小书是一笔可见的开销。
- 字符表最多 8128 个字符，超出的字符用 4 字节形式；实测 334 本中文书里只有 1 本用到。
- 单字节码固定 64 个。日、韩文用 112 个时再省 0.3–0.7%，但双字节码不够用，中文上也会变差；以后要支持就定义新的布局编号。

## 7. 资源项

- **存储方式 2**：原样保存。适用于已经压缩过的格式（PNG、GIF、WebP、WOFF2、音视频）。
- **存储方式 3**：整个成员压缩成一个 brotli 流。适用于没有压缩过的二进制（TTF、OTF）和不是 UTF-8 的文本。
- **存储方式 4**：存储字节是一个 Lepton 文件（Dropbox 设计的 JPEG 可逆再压缩格式），解码后得到成员的原始 JPEG 字节。
  2026-10-01 决定用 Lepton 取代原计划的 JPEG XL：阅读器总是把还原出的 JPEG 交给渲染器，用不到 JPEG XL 的图像格式；
  而现有的 Rust JPEG XL 实现对两类 JPEG 还原出错或崩溃。Lepton 在语料库样本上更小，纯 Rust 实现。
  - **定义**：Lepton 没有独立的格式规范，由实现定义。本规范引用的是 `lepton_jpeg` 0.5.8（Microsoft 的 Rust 移植，Apache-2.0），
    仓库里的 `third_party/lepton_jpeg/` 是它的一个 fork，在仓库里自行维护（改动只涉及拒绝什么输入、怎么拒绝，绝不涉及码流的格式，见该目录的 `EBK-CHANGES.md`）。
    一个存储方式 4 的成员是合法的，当且仅当这份实现把它的存储字节解码成长度和 CRC-32 都与成员表相符的字节。
    解码时用的是该库称为 `compat_lepton_vector_write` 的设置，也就是写入器编码时用的那一套（接受渐进式文件、拒绝 JPEG 标准不允许的 Huffman 表、
    拒绝带 0 的量化表、图像任一边不超过 16386 像素、两种算术变体由 Lepton 文件头里的标志决定），再加上下面的各项上限。读取器必须接受的文件及其解码结果的校验值，在参考实现的 `crates/ebk/tests/data/`（`*.lep`）。
    读取器核对长度和 CRC-32，所以别的 Lepton 实现即使行为有出入，也只会让成员读取失败，不会返回错误的字节。
  - **写入器**写入之前必须用读取器的解码路径实际还原一遍并逐字节比对；编码器拒绝、还原出错或崩溃、结果不一致、没有变小，都改用别的存储方式。
    实测用不上存储方式 4 的：没有 EOI 标记的渐进式 JPEG（Lepton 接受但还原出别的字节）、CMYK、抽样因子大于 2 的 JPEG。
    写入器只用 1 个分区（`max_partitions = 1`）：比 8 个分区小 0.5 个百分点，而 WASM 里的读取器本来就是单线程。
    宽 × 高超过 2^26 像素的图、平均每个 8×8 块不到 1 个字节的图（几乎空白）、扫描次数超过下面读取器规则的渐进式图、Lepton 压到不足八分之一的图，写入器不得使用存储方式 4（下面读取器的规则会让这样的成员读不出来）。
  - **读取器**：
    - 原始长度不超过 2^27（128 MiB），Lepton 文件头里记的长度必须等于成员的原始长度；输出限制在原始长度之内，随实际数据增长。
    - 必须有**像素数上限**（宽 × 高；默认 2^26，网页阅读器可以更低），超过时报"过大"。解码器在读任何图像数据之前就按图像尺寸分配系数内存，
      每像素最多 6 个字节，所以这个上限就是内存上限：一个几百字节的成员可以声明任意尺寸。
    - **工作量与实际存在的字节成比例**。解码器按图像尺寸分配并解码全部系数，不管后面有没有数据，所以必须把尺寸和真实的字节数联系起来：
      图像的 8×8 块数（宽 × 高 ÷ 64）不得超过原始长度的字节数，超过的按损坏处理；加上成员表里"原始长度 ≤ 8 × 存储长度"的规则，
      每个存储字节最多对应 8 个块。真实的图远在这个范围之内：语料库 4,421 张 JPEG 里只有 2 张平均每块不到 1 个字节，Lepton 最多压到原来的 1/3.4。
    - 渐进式图是一遍扫描一遍扫描写出来的，每遍扫描都要走一遍整张图的系数，而一遍扫描在文件里可以只占几个字节。所以
      扫描次数 × 全部分量的 8×8 块数不得超过原始长度的 16 倍，超过的按损坏处理。编码器一般写十遍左右；语料库里的 3 张渐进式图远在这个范围之内。
    - 文件头里只有一个线程交接表，最多 16 项，各项的起始行不递减；有多个表、项数更多或起始行倒退的按损坏处理。
      每一项都解码成自己的一份图像，没有这条规则，文件头可以让解码器把整张图分配很多遍。
    - Lepton 文件头（zlib 压缩的一段，里面是 JPEG 自己的头部、重启标记信息、图像之后的字节）解压后的总长度不得超过原始长度加 64 KiB；
      缓冲区随实际数据增长，分配失败是错误。上游实现在这里没有上限：zlib 可以膨胀一千倍，记录还可以重复，800 KB 的文件头曾经占到 1.6 GB。
    - 解码器是一大段不是为恶意输入写的代码。能捕获 panic 的环境里，panic 按"数据损坏"报告；在 WASM 里它是 trap，
      宿主应当重新建立实例并把该成员记为读取失败（不再重试它），并且给每次读取设时间上限。

**校验**：一次读出整个成员的接口，返回之前必须核对原始长度和 CRC-32。
流式读取的接口（用于大的音视频等存储方式 2 的成员）可以边读边交付，但必须在流结束时核对并报告不符。

## 8. 上限

阅读器会在浏览器里解析来源不可信的文件。上限分两类。

**格式上限**：写入器不得超过，读取器遇到超过的文件必须拒绝。所有读取器的结论相同。

| 项目 | 上限 |
|---|---|
| 索引的压缩长度、解压后长度 | 各不超过 64 MiB |
| 文本块数 B | 不超过 2^20 |
| 文本块的原始长度 | 1 到 2^24；除最后一块外不小于 4096 |
| 文本块和索引的压缩长度 | 不超过 n + n div 4096 + 64（n 是解压后长度） |
| 成员数 M | 不超过 2^20 |
| 路径长度 | 1 到 1024 字节 |
| 字符表 | 不超过 8128 个字符 |
| 存储方式 4 的成员的原始长度 | 不超过 2^27，且不超过存储长度的 8 倍 |

**读取器的资源上限**：必须存在，具体数值由读取器决定；超过时只是该次读取报"过大"，文件本身仍然合法。

- 单个成员的原始长度上限（本实现默认 1 GiB；网页阅读器建议 256 MiB），在分配内存之前检查。
- 存储方式 4 的像素数上限（第 7 节）。
- 会读取全部成员的工具（解包、校验）必须有可配置的**总输出上限**，并按成员表的顺序读取、缓存已解压的块，使总工作量与文本流长度成正比。
  理由：十几个字节的 brotli 流可以解出 16 MiB，一个十几 MB 的文件可以声明上千 GiB 的文本。
  上限按成员的原始长度累计，读取失败的成员也计入（工作可能已经做了）；读取器不支持的存储方式的成员不计入。
- 读取器必须记住解压失败的块，不得对同一个块重复解压。否则一个损坏的 16 MiB 的块上有几千个小成员时，每读一个成员都要重新解压一次。
  因为内存不足而失败的块同理：不应每读一个成员就重试一次（本实现记住它们，调用方要求时才重试）。
- 内存不足必须作为错误返回，包括解压器内部的分配（窗口、Huffman 表）：通用的解压库在分配失败时往往直接中止进程，在 WASM 里就是 trap。
- 打开文件时内存不足，应当报"过大"而不是"文件无效"：同一个文件在内存更多的环境里是合法的。
  读取器为每个成员保留的内存应当尽量少（本实现每个成员 40 字节加路径本身；2^20 个成员的文件，路径 5 字节时打开的峰值是 65 MiB，路径 51 字节时是 157 MiB）。
- "过大"是读取器自身条件的结论，不是文件的性质，所以不同环境可以不同：一个声明 2^32 字节以上的成员，32 位的读取器报"过大"，
  64 位的读取器可能读到数据才发现它是损坏的。两者都不得把它报成"文件无效"，也都不得返回错误的字节。
- 读取器不得因为索引里声明的长度就预先分配同样大小的内存；输出缓冲区应当随实际解出的数据增长。在 WASM 里内存不足是 trap，应当用可失败的分配。
- 读取器应当缓存至少 2 个解压后的块（非规范性建议）。

**错误的范围**：索引层面的错误（3.3 节的任何检查不通过）必须拒绝整个文件；
数据层面的错误（块解压失败、CRC-32 不符、码表或 Lepton 解码出错）只让受影响的成员读取失败，读取器可以继续提供其它成员。

**把成员写到磁盘的工具**（如 `extract`），除了 5.4 节的路径检查之外还必须：

- 只写进新建的或空的目录；
- 用"排他创建"的方式建文件，这样大小写或 Unicode 规范化意义上相同的两个路径会报错而不是互相覆盖；
- 拒绝含有 `: * ? " < > |` 的路径段、以 `.` 或空格结尾的路径段，以及主文件名（不分大小写、不计扩展名）是
  `CON`、`PRN`、`AUX`、`NUL`、`CONIN$`、`CONOUT$`、`COM0`–`COM9`、`LPT0`–`LPT9`，以及 `COM`、`LPT` 后面跟上标数字 `¹`、`²`、`³` 的路径段。
  这些在 Windows 上会指向盘符、设备或被悄悄改名；
- 拒绝超过 255 字节的路径段（常见文件系统的上限）；
- 在写出第一个文件之前，先检查完索引能告诉它的一切（上面的路径规则、不支持的存储方式、单个成员的上限、总输出上限）；写到一半失败时说明已经写了多少。

**把路径显示给用户的工具**应当转义不可见的字符（U+0080–U+009F、双向控制字符等）：路径规则只排除了 ASCII 的控制字符，其余的可以改变终端里显示的内容。

## 9. 从 EPUB 生成 EBK

规范性的要求：

- 成员以 ZIP 的**中央目录**为准：目录里的每个条目成为一个成员，路径取目录记录里的文件名字节，原样使用。
  文件名一律按 UTF-8 理解，不看"文件名是 UTF-8"的标志位（位 11）：EPUB 要求文件名是 UTF-8，而不少工具不设这一位；
  按这一位把名字当作 CP437 的读取器会得到别的名字，这是有意不跟随的。
  **目录条目**指文件名以 `/` 结尾的条目，不保存；它的名字去掉末尾的 `/` 之后必须满足 5.4 节的路径规则，
  长度和 CRC-32 必须为 0，数据必须为空（"存储"时压缩长度为 0，deflate 时是一个空的流）。其它条目（包括文件名以反斜杠结尾的）都是文件。
- 输入必须是 EPUB：没有 `META-INF/container.xml` 的 ZIP 不转换。
- 转换器为了决定成员的顺序会解析 `container.xml` 和 OPF。它们同样来自不可信的文件：解析之前必须限制实体展开和元素嵌套的深度
  （本实现：声明了实体或嵌套超过 256 层的不解析，成员保持 ZIP 里的顺序）。几百字节的 XML 可以展开成几个 GiB，或者让递归的解析器栈溢出。
- 不同的 ZIP 读取器对下列情况的处理不一致（有的从文件末尾的目录读，有的从头顺序读本地文件头），所以转换必须失败，不得猜测或改名。
  总的原则是：**按目录读和从头顺序读，必须得到同样的条目和同样的字节**。
  - **结束记录**：取"注释恰好在文件末尾结束"的那一个；没有这样的位置，或有不止一个（注释里可以藏一份完整的目录和结束记录），都拒绝。
    结束记录里"本盘条目数"与"总条目数"不相等；中央目录不是紧接在结束记录（有 ZIP64 时是 ZIP64 结束记录）之前，
    或者目录的长度与条目数对不上；ZIP64 的两份结束记录互相矛盾，或 ZIP64 结束记录不是 56 字节（带扩展数据）；分卷的 ZIP。
  - **文件名**：不是合法 UTF-8，或不满足 5.4 节的路径规则；两个条目文件名相同；
    条目带有 Info-ZIP Unicode Path 附加字段（0x7075，目录记录或本地文件头里），且其中的名字与文件名不同。
  - **本地文件头**与目录记录不一致：文件名、压缩方法不同；没有数据描述符（本地文件头的标志位 3；目录记录里的这一位不看）时 CRC-32 或两个长度不同。
    有数据描述符时：本地文件头里的 CRC-32 和两个长度必须全为 0，或者全与目录记录相同；描述符必须紧跟在数据后面，
    长 12、16、20 或 24 字节（有无签名、长度是 32 位还是 64 位），其中的 CRC-32 和长度与目录记录相同。
    "存储"（不压缩）的条目带数据描述符且本地文件头为 0 时，从头顺序读的读取器只能靠描述符的签名找到数据的结尾，所以数据里不得出现 `PK\x07\x08`。
    "存储"的条目两个长度必须相等。
  - **排列**：全部条目（含目录条目）必须从文件开头一个接一个排到中央目录，中间除了数据描述符之外没有别的字节，互不重叠。
    这排除了目录没有列出的本地条目、文件开头的额外数据和互相重叠的条目。
  - **数据**：条目被加密，或使用存储、deflate 以外的压缩方法；deflate 流没有恰好在压缩长度处结束（后面还有字节，或者没有结束块）；
    实际长度或 CRC-32 与目录记录不符。
- 转换器必须有可配置的**输入上限**（全部条目解压后的总长度，本实现默认 4 GiB），在读任何条目之前按目录里声明的长度检查；
  读条目时不得按声明的长度预先分配内存，读到超过声明长度一个字节就停下并报错。理由与第 8 节相同：300 KB 的 ZIP 可以解出 300 MiB。
- `mimetype`、`META-INF/` 下的文件作为普通成员保存。
- 转换器写完之后必须把每个成员读回来与 EPUB 里的字节比对，比对通过之后才让输出文件出现在目标位置（先写临时文件再改名）；不得覆盖输入文件。

写入器的建议做法（非规范性，本实现的做法）：

- **哪些成员进文本流**：原始字节是合法 UTF-8 的成员进文本流；其余作为资源项：以 `FF D8 FF` 开头的（JPEG，不看扩展名）试存储方式 4；
  其它已经压缩过的格式（按扩展名）用存储方式 2；剩下的试一次 brotli，变小就用存储方式 3。
  例外：EPUB 的 ZIP 把某个条目压小了（deflate 之后比原来短），说明它还压得动，这样的条目即使是"已经压缩过的格式"或 Lepton 没用上的 JPEG，也试一次 brotli。
  不这样做的话 EBK 会比 EPUB 大：语料库里有 7 本书（压缩得不好的 PNG、几乎无声的 MP3）因此大了 1–15%。
- **码表**：文本流里是合法 UTF-8 且含有非 ASCII 字符的成员可以用存储方式 1；纯 ASCII 的成员编码前后相同，留在存储方式 0，读的时候少一遍解码。
  整条文本流按"不用码表"和"用码表"各切块、压缩一次，连同各自的索引比较总长度，用码表更小才用（相等时不用）。代价是文本的压缩时间翻倍。
- **顺序**：`mimetype`、`META-INF/` 下的文件、OPF、导航文件、CSS，然后是按书脊顺序的正文，最后是其余成员。顺序不影响格式的正确性，对体积的影响也很小（实测 0.04–0.27 个百分点）。
- **切块**：目标块大小默认 4 MiB。整条文本流不超过目标大小时只有一个块。超过时：书脊之前的成员（OPF、导航、CSS 等）单独成为第一个块；
  之后在成员边界上切，下一个成员放不进当前块就另起一块；单个成员超过目标大小时按目标大小切开。
  会切出短于 4096 字节的块的地方不切：书脊之前的成员不足 4096 字节时，第一个块延伸到其后第一个使它达到 4096 字节的成员边界；别处则让当前块继续到目标大小。
- **块大小的依据**：全语料库上 4 MiB 相对整本固体压缩只大 0.1–0.2 个百分点，但那是被大量小书稀释的数字；真正被切开的书上代价是 3.1–3.3 个百分点
  （《宋史》16 MB：UTF-8 时 +4.4%，用码表后 +1.7%）。目标块大小最大可以设到 16 MiB。

## 10. 与 EPUB 渲染器的衔接（非规范性）

渲染器需要的只是"按路径取成员"：取文本、取二进制、取原始长度。原始长度直接来自成员表，不需要解压。
实测 foliate-js 在只提供这三个函数的情况下可以读出书名、章节和目录。

成员的媒体类型不在容器里记录，以 OPF 清单为准。

## 11. 符合性

- **读取器**：必须执行第 2–8 节里对读取器的全部要求（变长整数的形式、精确的 brotli 流和长度上限、文件结构、文本块、索引、码表解码、存储方式 4 的规则、上限），
  必须支持存储方式 0、1（布局 1）、2、3、4。
- **写入器**：只能写出通过上述全部检查的文件。
- **从 EPUB 生成 EBK 的转换器**：还必须满足第 9 节。

## 12. 已定的事项（非规范性）

1. **成员表不记录媒体类型**：OPF 清单里已经有，存两份会出现以谁为准的问题。以后需要的话加一个可选段。
2. **校验值用 CRC-32**：没有签名的话 SHA-256 也防不了篡改，而 2^-32 足以发现还原错误。格式明确不提供防篡改。
3. **不设整本书的内容标识**：文件哈希不需要格式支持。以后要做跨版本去重，可以在可选段里定义内容摘要。
4. **块的原始长度上限 16 MiB**：等于 brotli 的最大窗口，也限定了读取器的内存和延迟。
5. **码表单字节码固定 64 个**；块长度可变。
6. **JPEG 用 Lepton**，按"固定引用一份实现"的办法定义（第 7 节），不用 JPEG XL：阅读器总是把还原出的 JPEG 交给渲染器，用不到 JPEG XL 的图像格式；
   做决定时能还原 JPEG 的 Rust JPEG XL 实现还不够成熟。
7. **除最后一块外块长不小于 4096**。
8. **EPUB 的 ZIP 由转换器自己严格解析**，这样 EBK 文件不取决于读 EPUB 的是哪个 ZIP 库。

未定（都不改变格式）：真实书库里渐进式 JPEG 的占比（Lepton 往往处理不了）；长篇的默认块大小；可选段的标签分配（0x80 起，尚未分配；
书架用的元数据、每块的校验值、内容摘要、签名都是候选）。
